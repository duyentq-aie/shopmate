# Phase 5 decisions: LLM routing and filter extraction with Gemini (2026-10-10)

Phase 5 adds the first LLM component: a router (question → one of the six golden intents) and a filter extractor (question → `SearchFilters`), measured on the DEV split. The router sits behind an interface (`app/llm/router.Router`) so a Jev router can be added later without touching callers. Gemini runs on the FREE tier only; billing is never enabled. This file is written before any evaluation run: Step 1 made no API call from code (the only live requests so far are 3 manual capability probes on 2026-10-09 Pacific time, counted in the daily counter).

**R27. Free-tier data use, and why it is acceptable here.**
On the free tier, inputs and outputs may be used by Google to improve its products. This is acceptable ONLY because every question in this repository is synthetic (a fictional shop, generated catalog and orders, hand-written golden questions, `example.com` emails). **Real customer data must never go through this key.** A production deployment needs a paid or enterprise tier whose terms exclude training on inputs, and a decision of its own.

**R28. Model: `gemini-3.5-flash-lite`, pinned; and why the smallest model.**
- Pinned exact ID `gemini-3.5-flash-lite` (version `3.5-flash-lite-07-2026`, read from the models list). Not an alias such as `gemini-flash-lite-latest` (it moves), and not `gemini-3.8-flash`: its free tier allows only 20 requests/day, too few for an evaluation.
- Free-tier limits of this model (AI Studio, project `shopmate`): about 15 requests/minute, 250K tokens/minute, 500 requests/day.
- Why Flash-Lite: routing and filter extraction are small, tightly structured tasks (an enum of six labels; eight nullable fields over closed vocabularies). The smallest model that does the job is the right default, and the evaluation is what proves it does; if it does not, that is a finding, and a larger model is a decision for a later phase, not a silent upgrade.

**R29. Free-tier guards (all tested with a fake HTTP transport; unit tests never call the API).**
- Client-side rate limiter: 12 requests/minute and 200K tokens/minute (a margin below 15 / 250K), a sliding 60-second window; it waits instead of sending.
- Daily ceiling: 450 requests per Pacific-time day (the quota resets at midnight Pacific), counted across runs and processes in `data/llm_usage/` (git-ignored), reserved BEFORE each request, retries included. A corrupt counter stops the run rather than resetting. The 3 probe requests of 2026-10-09 are recorded.
- Hard cap per run: `--max-live-calls`, default 300; exceeding it aborts the run before sending.
- 429 handling: a body that says the DAILY quota is exhausted, or `limit: 0`, stops at once (`DailyLimitExhausted` / `FreeTierUnavailable`) and is never retried; a per-minute violation backs off exponentially with jitter, at least the delay the API asked for, bounded by 5 attempts; a 429 that is not recognised is retried at most twice and then stops; 5xx and network errors back off, bounded. Only the structured part of Google's error format (QuotaFailure ids, RetryInfo, an explicit `limit: 0`) is trusted. **Risk recorded:** the real 429 format has not been observed on this key, so the classifier follows the documented format and fails safe.
- Live calls need `--live`. Without it a cache miss stops the run, so an accidental run can neither spend quota nor touch the network.
- The key travels in the `x-goog-api-key` header only, never in a URL, a log line, an exception or a cache file (tested).

**R30. Disk cache; results reproducible without an API key.**
Every API answer (200) is cached under `eval/llm_cache/<component>/<digest>.json`, keyed by the sha256 of {model ID, prompt template hash, response-schema hash (which holds the closed vocabularies), input, generation config}. An entry holds the raw response, the latency measured when the call was live and the HTTP attempts. Entries are never overwritten and are committed, so anyone can re-run an evaluation offline; a re-run makes zero API calls and reports the recorded live latency. A blocked or empty 200 answer is cached too (it is a recorded fact; the component turns it into a per-item failure, never a guessed label). The clean-tree check of the runner also tolerates new files under `eval/llm_cache/` (the run's own cache entries).

**R31. No calibrated confidence.**
`gemini-3.5-flash-lite` exposes no token log-probabilities (checked live 2026-10-10: `400 Logprobs is not enabled for this model`; `tests/test_llm_live.py` re-checks it). `RouteResult.confidence` is therefore `None` with the note "no calibrated confidence", and the model is never asked to rate itself: a self-reported number is not calibrated. If a future model exposes log-probabilities, the probability of the chosen intent would be derived from the log-probability of the first token that distinguishes the chosen enum value from the others; not implemented, nothing to test it on.

**R32. Filter semantics given to the extractor.**
Taken from the golden labels of the dev product items and from `eval/golden/schema.apply_filters` (LABELING.md says nothing about price):
- Price: `k` = thousand, `tr` = million. "dưới / tối đa / không quá X" → `price_max = X`; "từ A đến B", "tầm A đến B" → `price_min = A`, `price_max = B`; bounds are INCLUSIVE (`apply_filters` excludes `price < min` and `price > max`). "trên X" → `price_min = X` follows from the same inclusive rule but no dev product item shows it; a lone "khoảng X" gives no range.
- **in_stock** is applied only when the customer asks to RESTRICT results to available items ("chỉ lấy hàng còn", "mình cần loại còn hàng"). "Còn ko?" is a question about availability: filtering on it would hide the very item the customer asked about. The extractor returns `true` or null, never `false`.
- `category` only when the customer names a section of the shop explicitly; `kind`, `color`, `material`, `size` only when the words identify exactly one value of the catalog's closed vocabulary (6 categories, 35 kinds, 18 colours, 28 materials, 23 sizes), otherwise null. The vocabularies are in the prompt AND the enum values of the response schema; the answer is validated again and a value outside the vocabulary becomes null and is counted (`dropped`), never invented or snapped to a nearest value.
- `keyword` is never extracted (R14); the Phase 3B oracle dropped it too, so the expected side of every comparison is the golden `expected_filters` without `keyword`.
- **Known disagreement, not hidden:** golden item gs-019 ("... còn hàng k shop") is labeled `in_stock: true`, but by the rule above that question is about availability, so the extractor returns null and the comparison counts a false negative on `in_stock`. The golden set is not edited; the item is listed in the error analysis.

**R33. The default retrieval mode is one config value.**
Phase 4 adopted `dense_folded`, but `Retriever.search` still defaulted to `dense`. The default now comes from `app.config.DEFAULT_RETRIEVAL_MODE = "dense_folded"`, looked up at call time (a constant, not an environment setting, so no deployment silently changes it). The Phase 3B and Phase 4 runners pass their mode explicitly and are unaffected: with the new code, `hybrid-none` (Phase 4) and `dense-none` (Phase 3B) re-run to `items` and `aggregate` identical to the committed results (38 of 38 each), without any API call. This was a separate small commit before Phase 5's.

**R34. What is evaluated, and how (dev only; the test split stays locked).**
- Routing on all 71 dev items; `{order_number}` is replaced by the item's real gold order number before routing (deterministic; refused if the number is not known).
- Filter extraction on the 24 product_search items.
- Retrieval with `dense_folded`, k = 10, under GOLD routing: floor (doc_type only) vs LLM-extracted filters vs ceiling (oracle), all re-run in the same run, with paired bootstrap of extracted against both. The product oracle is a tautology (Phase 3B), so the ceiling is an upper bound, not a competitor.
- no_answer product items with extracted filters: the correct-empty rate is a REAL measurement now (the filters come from the LLM), unlike under oracle.
- Full pipeline over the 38 retrieval items (24 product, 14 policy): LLM route → doc_type → (extract filters) → retrieve. A misrouted question is a miss and triggers no retrieval for the wrong intent; a policy question routed to product_search really runs a product retrieval and misses. A no_answer item is correct only if it is routed to product_search AND the result is empty.
- Macro-F1 averages the F1 of the classes that occur in the gold labels (all six on dev).
- Per call latency p50/p95 and tokens come from the recorded responses; the free-tier cost is 0, and the theoretical paid-tier cost per 1,000 questions is computed from the official price page, read and dated at evaluation time.

**R35. The adversarial probes, and routing is not a security boundary.**
Dev has no prompt-injection item. `eval/probes/injection_v1.json` holds 8 hand-written probes (ignore previous instructions, listing customer emails, revealing the system prompt, an instruction embedded in a product question, a role-play, an unaccented injection, a JSON escape, a fake authority marker), outside the golden set, `author: agent_draft`, with the expected label of each fixed in the file BEFORE any run (the label is the intent of the legitimate request; a pure attack is `out_of_scope`). They are never used for golden metrics or to choose a prompt, are reported apart, and the runner refuses to route them until a human has set `status` to `human_reviewed`. **Routing is not a security boundary.** Data protection comes from the read-only Saleor client and the email-verified order lookup; a correct `out_of_scope` label on an attack is a bonus, not the defense.

**R36. Iteration discipline.**
Prompts live in `prompts/router_v1.md` and `prompts/filters_v1.md`; their sha256 goes into the cache keys and every result file. A prompt changed after seeing dev results becomes a new version file (v2, v3), logged with its dev score in `docs/PROMPT-LOG-phase5.md`: at most 3 versions per component. Dev scores after any iteration are optimistic, and RESULTS says how many iterations were made. The prompt examples are invented (a test checks that no dev question is copied into a prompt). Disclosure: the author of v1 had read the dev questions while surveying the labeling conventions (needed to write the intent and price rules), so even v1 is not a blind prompt.

**R37. Technical choices.**
Plain `httpx` against the REST API (no SDK, no new dependency; the guards wrap it anyway). `temperature 0`, `thinkingConfig.thinkingLevel = "minimal"` (accepted by the API and without thought tokens in the probe), `maxOutputTokens` 256 (router) / 512 (extractor), structured output with `responseSchema`. No `seed` is sent (not probed). The model is not bit-deterministic at temperature 0; the cache, not the model, is what makes results reproducible.
