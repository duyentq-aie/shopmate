# Trace monitor: decisions (2026-10-10)

`app/monitor.py` serves the dashboard page and the tail of the request traces. Run it with `uv run python -m app.monitor` (default `http://127.0.0.1:8765/monitor/`). It only reads; nothing in the pipeline imports it, so it cannot change how a request is handled.

**M1. Three routes, two files, nothing else.** `GET /monitor/` returns `dashboard/index.html`; `GET /monitor/api/traces?limit=N` returns the last N lines of `logs/traces.jsonl` as `text/plain` (default 5000, 1 to 20000, anything else including a non-number is **422**; a missing or empty file is 200 with an empty body); `GET /monitor` answers 307 to `monitor/`. Both file paths are fixed when the app is built, so no request can name a file. There are no path parameters, no static mount, no directory listing, and no `/docs`, `/redoc` or `/openapi.json`. Tests send `..`, encoded dots and slashes, NUL bytes, `//`, `;` and query keys such as `file=` and `path=` to the app unnormalised and check that nothing but the two files is ever opened (a spy on `open`) and that a secret file next to them never appears in any response.

**M2. Loopback only. No token mode (owner decision).** The launcher binds `127.0.0.1` (port 8765, `--host`/`--port` or `MONITOR_HOST`/`MONITOR_PORT` from the environment or `.env`) and **refuses to start** on any host that is not a loopback address (`127.0.0.0/8`, `::1`, or the name `localhost`) with a message, before anything is opened. A first version had an optional `MONITOR_TOKEN` for non-local binds; the owner dropped it: nothing in this app reads such a setting, and setting one changes nothing (a test). **Remote access, if ever wanted, goes behind a reverse proxy with real authentication, not into this app.**

**M3. Defence in depth: a guard on every request (owner decision).** Even if the app is started some other way, such as `uvicorn app.monitor:app --host 0.0.0.0`, an ASGI guard in front of every route answers **403** to any request whose peer address is not loopback, before routing (so 404s, 422s and redirects cannot leak either). Details that matter:
- It checks the socket's peer address. It reads no header: `X-Forwarded-For`, `X-Real-IP`, `Forwarded` and `Host` are never believed. A request with no peer address, or one that is not an IP literal (`localhost`, `testclient`), is refused: the guard fails closed.
- IPv4-mapped IPv6 addresses are unwrapped (`::ffff:127.0.0.1` is loopback, `::ffff:192.168.1.10` is not). Odd spellings (`127.1`, `0x7f.0.0.1`, `2130706433`, trailing blanks) are not loopback.
- The launcher passes `proxy_headers=False` to uvicorn. With plain `uvicorn --host 0.0.0.0`, uvicorn trusts forwarding headers only from `127.0.0.1` by default, so a remote peer cannot claim to be local; this is tested end to end with a real uvicorn server on `0.0.0.0` and a request from this machine's own non-loopback address (403, with and without a forged `X-Forwarded-For: 127.0.0.1`), and the default launcher is shown to listen on `127.0.0.1` only.
- **Limits.** (a) `uvicorn --forwarded-allow-ips '*'` makes uvicorn believe forwarding headers from anyone and defeats the guard: do not use it. (b) A reverse proxy on the same machine connects from `127.0.0.1`, so the guard lets through everything it forwards: **the proxy must do the authentication**. (c) The guard is not a substitute for the bind: the supported way to run the monitor is `python -m app.monitor`.

**M4. The trailing slash.** The page fetches the *relative* path `api/traces`, which resolves to `/monitor/api/traces` only when the page is at `/monitor/`. At `/monitor` (no slash) it would resolve to `/api/traces`, a 404. So `/monitor` redirects to `/monitor/` with **307** (not a cached 301/308) and a *relative* `Location: monitor/`, which also works behind a path prefix. Tests resolve the real page's fetch target with the browser's URL rules and request it from the real app.

**M5. Reading the file from the end.** `tail_lines` reads backwards in 64 KiB blocks until it has `limit + 1` newlines, the start of the file, or 32 MiB + one block, so memory follows the lines asked for, not the size of the file: a test on a 34 MB file with 200,000 lines allocates under 4 MB for 5000 lines and under 10 MB for 20,000 (measured with `tracemalloc`; at most two copies of the lines are alive at once). Rules: the size is read once, so lines appended while reading are not part of the answer; **a last line without its newline is dropped** (a writer is in the middle of it); the oldest line is dropped when a block boundary may have cut it; if the lines exceed **32 MiB** the oldest whole lines are dropped until they fit (a single line bigger than that gives an empty answer). The file is opened `rb`, never written.

**M6. Headers on every response, including errors.** `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, and the owner's CSP, exactly: `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src https://fonts.gstatic.com; connect-src 'self'; img-src 'self' data:; frame-ancestors 'none'`. `'unsafe-inline'` is there because the page's script and style are inline, so the CSP limits where the page may load from and connect to and forbids framing, but does not stop an injected inline script. Trace lines contain model output and customer questions (emails and keys are masked at write time, nothing else): whatever renders them must treat them as text, never as HTML.

**M7. What the monitor does not do.** No authentication, no HTTPS, no writes, no rotation or trimming of the trace file, no search or aggregation on the server (the API returns lines, nothing else).

**M8. Checking the real page in a browser (2026-10-10).**
*Method.* Headless Chrome for Windows (155.0.8059.39), started from WSL with a throwaway `--user-data-dir` inside the session scratchpad (never the owner's profile), against the real monitor app (`create_app`, `parse_bind`, `make_config`, the guard and the routes) over a temporary trace file; console messages were written to a log file. Time was the browser's virtual clock (`--virtual-time-budget`), the network is real. Windows reached the server through WSL's localhost forwarding and the loopback guard accepted it. Every Chrome process and server was started and ended by the check; none was left running. The trace lines were written by the real `Tracer`, not by hand, so the page was also tested against the real file format. *Positive control:* the same harness against a deliberately bad page (external script, `fetch` to another origin, external image) logged all four CSP violations, so an empty console log means something.

The verified version above (md5 `b8d14e8c…`) differed from today's file by exactly one string: the example address in the page's help text said `http://127.0.0.1:8080/monitor/`, now `http://127.0.0.1:8765/monitor/` (the monitor's default; same byte length, md5 now `7915a33e…`; undoing the one string reproduces the verified md5). `test_the_example_address_in_the_real_pages_help_text_is_the_monitors_default_address` keeps the page and `app.monitor.DEFAULT_PORT` from drifting apart again (shown to fail on the 8080 version).
