# Request tracing: decisions (2026-10-10)

One JSON line per request in `logs/traces.jsonl` (git-ignored), written by `app/tracing.py`. No behaviour change: spans are no-ops outside a request, exceptions are recorded and re-raised untouched, and a failing log write only prints `trace write failed` on stderr. Proven, not just tested: with the instrumentation in place, the offline replay of the Phase 5 evaluation (0 live calls) and the Phase 3B/4 baselines (`hybrid`, `dense`, `dense_folded`) give results identical to the committed ones.

**T1. Schema (exactly these keys; checked by `app.tracing.validate_trace_line`).**
`trace_id`, `ts` (ISO UTC, milliseconds, `Z`), `question`, `intent` (one of the six or null), `status` (`ok` | `warn` | `error`), `spans[]` (`stage`, `start_ms`, `duration_ms`, `model`, `tokens_in`, `tokens_out`, `cache_hit`, `error {type, message} | null`) and a top-level `error {type, message} | null`. `start_ms` and `duration_ms` are milliseconds from the start of the request. `status` is `error` if the request has an error, `warn` if only spans have one (the request went on), `ok` otherwise; the validator checks that it agrees.

**T2. Where a request is.** There was no request handler in the repository (the router, extractor and retriever were only called by the evaluation runner), so `app/pipeline.handle_question(question, router=, extractor=, retriever=, tracer=)` is the first request path (owner-approved 2026-10-10; marked in the code as the **interim entry point until the Phase 6 agent loop**, which will replace it): router, then (product_search only) extractor, then retrieval, with the same routing rules as the Phase 5 evaluation pipeline. Its tracer is optional; without one nothing is traced. The evaluation runner is NOT traced (its calls are stage by stage across 71 questions, not one request each, and it would flood the log). The stages `order_lookup`, `ticket_confirm`, `reply` and `answer` are part of the schema and of the `span()` API; nothing emits them yet because those components do not exist (owner-approved: they stay in the schema and the `span()` API so Phase 6 needs no schema change).

**T3. Tokens are the Gemini `usageMetadata`, never estimates.** `tokens_in` = `promptTokenCount`, `tokens_out` = `candidatesTokenCount` + `thoughtsTokenCount` (the billed output). A response without `usageMetadata` gives `null`. A cache hit carries the metadata recorded with the cached answer and `cache_hit: true` (it was not billed again, so sum tokens over `cache_hit: false` spans for cost). Retrieval spans have `model` = the embedding model and no tokens.

**T4. Nothing secret or personal is written.** Emails become `[email]` in the question and in every message; API keys, tokens and passwords become `[secret]`: the values configured in the environment or `.env` whose name contains KEY, TOKEN, SECRET or PASSWORD, any `AIza…` key, `Bearer …` values and `name=value` / `name: value` assignments of such names. Tests check the written file for the literal secrets and emails after successful requests and after failures that echo them. Not covered: other personal data in a question (names, phone numbers, addresses).

**T5. error.type: one type per real cause, nothing mapped to the nearest one (owner decision 2026-10-10, replacing my first version).**
A first version used the closest agreed type when the cause had no exact one (a 5xx after exhausted retries was `llm_429_minute`, every Saleor failure was `saleor_timeout`, our own caps were `llm_429_daily`). The owner rejected it: **a trace must never claim a cause that did not happen** (a real outage would look like a recovered warning). Every failure now has its own type; the real cause is also in `message`.

| error.type | Level | Exactly when | Source in the code |
|---|---|---|---|
| `llm_429_minute` | **warn only** | a *recognised per-minute* 429 was retried **and the call then succeeded** | `LiveResponse.minute_429_retries` > 0, reported by `GeminiClient`, carried by `GenResult`, recorded by `SpanRecorder.record_response`. Never produced from an exception; `fail()` refuses it and the validator rejects it as a request's `error` |
| `llm_429_daily` | error | Google's own daily-quota 429 | `DailyLimitExhausted` |
| `llm_rate_limited` | error | a 429 (per-minute or unrecognised) on every attempt: retries exhausted | `RetriesExhausted(cause="rate_limit")` |
| `llm_unavailable` | error | 5xx or network failure, retries exhausted | `RetriesExhausted(cause="server_error" or "network")` |
| `llm_request_error` | error | HTTP 4xx from the API (400, 403, 404, ...), not retried; also a 429 with `limit: 0` | `ApiError` with 400 <= status < 500; `FreeTierUnavailable` |
| `llm_cache_miss_offline` | error | cache miss while running without `--live` | `CacheMiss` |
| `budget_cap_reached` | error | **our** daily ceiling (450) or per-run cap; nothing (more) was sent | `DailyBudgetReached`, `CallCapExceeded` |
| `llm_invalid_output` | error (request) / warn (extractor) | the model answered but nothing usable came out: not JSON, outside the enum, blocked | `BadResponse`; the router's and the extractor's own unusable-answer checks |
| `filter_out_of_vocab` | warn | the extractor dropped a value (closed vocabularies, invalid price); message names the fields, not the values | extractor |
| `qdrant_unreachable` | error | the transport to Qdrant failed (connection refused, timeout) | `ResponseHandlingException` whose `source` is an `httpx.TransportError`; a raw transport error in the retrieval stage |
| `saleor_timeout` | error | a **real timeout** talking to Saleor | `SaleorQueryError` whose `__cause__` is an `httpx.TimeoutException`; a raw timeout in `order_lookup` / `ticket_confirm` |
| `saleor_error` | error | any other `SaleorQueryError`: unreachable, HTTP status, GraphQL error | other `SaleorQueryError`; a raw non-timeout transport error in those stages |
| `readonly_violation` | error | the read-only client refused a request | `ReadOnlyViolation` and subclasses |
| `request_interrupted` | error | `KeyboardInterrupt` (Ctrl+C) or `SystemExit` (`sys.exit()`) ended the request before it finished; the exception is re-raised, never swallowed | `KeyboardInterrupt`, `SystemExit` |
| `internal_error` | error | **not in any list the owner gave; approved 2026-10-10.** Any other exception (a bug); without it such a request would be untraceable | everything else |

*Types I had to add, for the owner to confirm or rename.* The owner's list has no type for a 429 whose retries are exhausted, and requires it to be an error and never `llm_429_minute`: I added **`llm_rate_limited`** (a 429 that never recovered; the message says per-minute or unrecognised). A 429 with `limit: 0` is `llm_request_error`, not `llm_429_daily`: the response says this key has no quota for this model, not that today's quota is used, and "come back tomorrow" would be wrong advice.

*What is deliberately not claimed.* An exception that fits none of the above stays `internal_error` with its message: a `RetriesExhausted` with no recorded cause, an `ApiError` with a non-4xx status, `CacheCorrupt` and any other `LLMError` (a local file problem is not the model's output), a `ResponseHandlingException` whose source is not a transport failure (Qdrant answered, we could not read it). The word "timeout" in a message is never evidence of a timeout; only the cause class is. A Qdrant read timeout counts as `qdrant_unreachable`: the name is the owner's, and the message keeps the real error class.

*Not traced.* A call that recovered from a 5xx, a network error or an unrecognised 429 leaves no mark (the schema has no field for retries, and only a recognised per-minute 429 has a type that says exactly that). `http_attempts` is in the LLM cache entry, not in the trace.

*How the recovered warning stays honest.* The client counts the per-minute 429s it retried and reports the count with the successful response. The count is **not** stored in the cache (a cache hit made no call, so it has nothing to report; the cache format and every cache key are unchanged). If the call then fails in some other way, that failure replaces the warning on the span, and the warning can never become the error of the request. Tests: `tests/test_request_tracing.py` triggers each type with the real `GeminiClient` over a fake transport, the real Qdrant client on a closed port and the real read-only Saleor client; `tests/test_tracing.py` checks the mapping per exception class and that no exception ever maps to `llm_429_minute`.

**T6. Interrupts end a request: traced as an error, never as a success, never swallowed (owner decision 2026-10-10).** `Tracer.request` and `span()` used to catch only `Exception`. Ctrl+C (`KeyboardInterrupt`) and `sys.exit()` (`SystemExit`) are `BaseException`s, so a request they cut short was written as `status: "ok"` with no error: a trace claiming a success that did not happen (found while writing `scripts/demo_requests.py`). Now both catch `BaseException`:
- `KeyboardInterrupt` and `SystemExit` become `request_interrupted` (status `error`; the message names which one, and for `SystemExit` its code), on every open span and on the request, the line is written, and the **same exception object is re-raised**. A test per case checks the identity (`caught.value is boom`), including when the log write itself fails.
- **`GeneratorExit` is the exception to the rule**: it is how Python closes a generator that holds a request or a span open (`gen.close()`), not a failure, so it passes through untouched and records nothing (the line is still written, `status: "ok"`, no error). Tests: raised inside a span and a request, and a real generator closed with `close()`: it must return normally, with no `RuntimeError` and nothing yielded again. An interrupt thrown into such a generator (`gen.throw(KeyboardInterrupt())`) is traced and comes out.
- Any other `BaseException` (a custom one) is recorded as `internal_error` with its class name, never as a success, and re-raised. `asyncio.CancelledError` falls here today; nothing in the app is async yet. If cancelled requests should be `request_interrupted` too, that is one more class in `classify_exception`.
- A recovered `llm_429_minute` warning on the span an interrupt ended is replaced by `request_interrupted` (the failure wins over the warning, as for any exception).
- `Tracer._write` still catches only `Exception`: an interrupt that arrives while the line is being written is not hidden.
- The dashboard knows the type (label "Request bị ngắt giữa chừng", severity error); `test_the_real_page_knows_every_error_type_the_tracer_can_write_and_no_other` keeps the page's list and `ERROR_TYPES` equal.
