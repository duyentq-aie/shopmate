# Phase 6 decisions: the bounded agent (2026-10-10)

Approved by the owner on 2026-10-10 after the survey and plan. The mechanics are in `docs/AGENT-DESIGN.md`; this file records what was decided, why, and what is pre-registered before any number exists. The test split stays locked and this phase never sets `final_evaluation`.

**A0. Test-split exposure: one question text was seen (owner decision).**
*What happened.* During the Phase 6 survey a `grep -n` over the raw golden file printed the text of one test-split question (its text only; no id, no label). It was not used in any prompt, test, example or document, and the golden file was not reopened to find which item it is.
*Fingerprint.* SHA-256 of the exact UTF-8 text of that question as stored in the golden file (the placeholder `{order_number}` literal, no normalisation, no trailing newline), recorded from the author's own context only:

`3b9975a677521f1dda7bac87ffa7098bc3d748f5724545ee185947a1e86d8692`

*Pre-registered, before any test score exists.* The Phase 8 report gives the test score **on all test items AND on the test items excluding the one whose question hash equals the value above** (matched at report time by hashing every test item's `question` field the same way; if no item matches, the report says so). Nobody looks up that item's id before then.
*From now on.* Golden items are read only through `eval.golden.loader.load_split("dev")`. `tests/test_golden_access.py` fails if any module outside `eval/golden/` names `GOLDEN_PATH`, `load_golden` or the path of `golden.vi.json`. Two things changed to make that true: the provenance hash of the golden file moved into `eval.golden.loader.golden_file_sha256()` (the runners called `file_sha256(GOLDEN_PATH)`; the value written to the result files is the same), and three tests of the golden tooling itself (`test_golden.py`, `test_frozen_test_split.py`, `test_merge_human_items.py`, which check the schema, the frozen test-split hash and the merge, so they must see every item) are listed by name as the only exceptions.

**A1. A workflow with bounded loops, not an open agent.** The router already decides the intent. The LLM is used only to route, to extract product filters and to write a grounded answer (product, policy, order status). Every loop has a bound and an exit (A4, A5, A7, A9, A12); the per-turn graph has no cycle except the confirmation self-loop, which is bounded.

**A2. Follow-up turns are parsed by rules, not by the LLM.** While the agent waits for an email, an order number or a yes/no, the next message is read with deterministic parsers (`app/agent/parsing.py`). If the message contains no slot it was waiting for, it is treated as a new message and goes to the router. Product follow-ups ("what kind of item?") always go to the router, then the extractor runs on the original request plus the reply.

**A3. Only three kinds of text are LLM-written.** Product answers, policy answers and order-status answers. Questions to the customer, refusals, hand-offs, small talk, out-of-scope replies, the ticket summary and the step-cap message are fixed templates (`app/agent/templates.py`), so a refusal can never leak anything.

**A4. Filter relaxation (owner-approved, pre-registered).** When a product search with the extracted filters returns 0 hits, it is retried **once**, dropping the first constraint present in the fixed order `size`, `color`, `material`. **`kind`, `category`, price and `in_stock` are never relaxed.** The reply starts with a fixed sentence saying that nothing matches all the constraints and names the dropped constraint before any suggestion. *Scoring of the `no_answer` items (written as code, `eval/phase6_scoring.py`, before any evaluation run):* an item is correct iff the answer explicitly says that nothing matches all the constraints **and** every relaxed suggestion states which constraint was dropped. An item for which the first search already returned hits is incorrect (the agent claimed a match the golden set says does not exist).

**A5. "Vague" product request.** The extractor returned neither `kind` nor `category`. The agent asks what kind of item (at most 2 clarifying turns for one request), then searches with what is known. All 24 dev product items have a `kind` or a `category`, so no dev item is affected.

**A6. Tickets (owner-approved).** The only write action. A ticket about an order needs the order number AND the owner's email to match (A7); a ticket without an order asks for a contact email (one clarifying turn). The agent shows a summary and **waits for an explicit yes** (a LangGraph `interrupt`, in a node of its own with no span). Anything that is not clearly a yes is not a yes: an unclear answer is asked again once, then the ticket is cancelled. The idempotency key of a ticket is a hash of conversation id, order number and summary. Tickets go to `data/tickets/tickets.jsonl` (git-ignored) with the customer's email in clear (local file, synthetic data); the email never reaches the LLM or a trace line. There are no Saleor writes anywhere.

**A7. Order verification and the 3-failure rule (owner-approved).** Order details are revealed only when order number and the owner's email match (D28, D37). Number only: ask for the email. Phone only: ask for the email. Mismatch, unknown number, or someone else's order: the same fixed refusal, so the answer never says whether the order exists. **After 3 failed verifications, order lookup is disabled for the rest of that conversation.** *Known gap, stated now:* the counter lives in one conversation, so a **new conversation resets it**; a real deployment needs a limit per order number or per caller (not built here).

**A8. What `lookup_order` returns.** Number, status, creation date, lines (name, SKU, quantity, quantity fulfilled), fulfilment status, dates and tracking number. No address, no phone, no email. The read-only query does not even select an address or a phone; the owner's email is used for the comparison inside the tool and goes no further.

**A9. Step cap.** At most 8 graph steps per turn, counted in the state, with LangGraph's `recursion_limit` as a backstop. The limit is 10 = 8 steps + the start step it counts + the one step the counter refuses: with 9, LangGraph raises its error before the 9th node can run, so the counter's own safe reply and trace would never fire (a mutation test found this; the first plan said 9). The longest legitimate path is 7 nodes. Hitting the cap ends the turn with a fixed safe reply and the request error `agent_step_cap_reached`.

**A10. Spans and taxonomy.** Stages: `retrieval` (search tools), `order_lookup`, `ticket_confirm` (proposing and writing a ticket), `answer` (the LLM answer), `reply` (fixed templates). Three error types were added to the tracer, the dashboard and `DECISIONS-tracing.md` together: `answer_guardrail_fallback` (warning of one span), `agent_step_cap_reached` (error), `ticket_write_failed` (error). A refusal, a hand-off or a lookup disabled after 3 failures is a normal outcome, not an error.

**A11. Guardrails after generation (Step 3), including the owner's addition.** Every price, stock status, order status and clause number in an answer must appear in the tool results; otherwise the generated text is discarded, a fixed template is sent and the span carries `answer_guardrail_fallback`. Numbers from the customer's own message may appear **only as their budget, never as a fact about a product**. **Rule: any price in the same sentence as a cited SKU must equal that SKU's price from the tool result.** The attack to test: "áo này 99k đúng không shop?" when the real price differs. The answer must not confirm 99k, and a fabricated confirmation must trigger the fallback. No email, phone or address in the answer except the customer's own email, masked. With no grounding the agent says the shop does not know, without calling the LLM.

**A12. `handle_question` (Step 3).** Keeps its signature and delegates to the agent; `PipelineResult` gains `reply`. `scripts/demo_requests.py` keeps working (it will use about 5 more live calls, for the answers).

**A13. Synchronous only.** LangGraph `invoke`, the Gemini client, Qdrant and Saleor are all synchronous, and single-node steps run on the calling thread. The addendum on `asyncio.CancelledError` therefore does not apply: it stays `internal_error`, as T6 says. A test fails if an `async def` appears in `app/agent/`.

**A14. Dependencies.** `langgraph==1.2.14` (with `langgraph-checkpoint 4.2.0`, `langgraph-prebuilt 1.1.0`, `langchain-core 1.6.9`, `langsmith 0.14.7`; 21 new packages, none of the existing ones changed). LangSmith tracing is off unless configured; a test checks it. The checkpointer is `InMemorySaver`: conversations live in memory only. A persistent one (`langgraph-checkpoint-sqlite` or `-postgres`) would also need a retention policy and a decision about storing emails on disk; lost conversations are safe (no confirmation, no ticket).

**A15. Pre-registered evaluation rules so far (more are written before the first number of each step).** Product items: the answer cites at least one gold SKU (a SKU the answer shows, not one merely retrieved); `no_answer` items: A4. Policy items: the answer cites the gold file and clause. Order and ticket items: the behaviour (answer, ask_for_verification, refuse) matches the label exactly; for tickets, no ticket without a confirmation turn, with both a yes and a no simulated. Out-of-scope and small talk: no tool call and a polite reply. The answer prompt has at most 2 versions in this phase, each logged in `docs/PROMPT-LOG-phase6.md`; the rule for keeping a second version is written down before the first dev number. Dev is optimistic for anything tuned on it.

**A16. Budget.** Gemini free tier, ceiling 450 requests per Pacific day, counted across runs. At the start of Phase 6: 13 used today, reset at 00:00 Pacific (14:00 in Vietnam until 1 November, 15:00 after). Router and extractor answers for the first turn of every dev question are already in `eval/llm_cache` (same prompts, same text). Expected new calls: about 38 answers per prompt version on dev plus 60 to 70 for the scripted multi-turn cases. A run that would pass 450 stops at a clean point and resumes after the reset.

**A17. Whether an `answer_v2` may exist: pre-registered (owner decision), written before any evaluation number.**
*Error types.* Only errors that the TEXT of the answer step can cause count, and they are exactly these three, taken from the per-item records of the v1 run:
- **E1 guardrail fallback by rule:** an item whose generated answer was rejected, counted per rule code (`price_mismatch`, `price_not_in_evidence`, `stock_mismatch`, `no_sku_cited`, `no_clause_cited`, `unknown_clause`, `order_status_mismatch`, ...). Items with the same rule code are one error type.
- **E2 missing SKU:** a product item with gold SKUs that is incorrect although a gold SKU was among the hits given to the answer step (`retrieved_skus`), so that routing, extraction and retrieval are not to blame.
- **E3 missing citation:** a policy item that is incorrect although the gold clause was among the hits given to the answer step (`retrieved_clauses`).
Routing, extraction, retrieval, order verification, ticket handling, the fixed templates, the scoring rules and the guardrail rules themselves are NOT error types for a new prompt: they are reported, not tuned.
*Allowed.* An `answer_v2` may be written **only if at least one error type affects at least 2 dev items**, and then it may target only the error types that do. At most one new version (v2) exists in this phase; it is logged in `docs/PROMPT-LOG-phase6.md` with the error type it targets, and v1 is kept as it is.
*Adopted.* v2 replaces v1 **only if it does not lower any intent's score** (the number of correct dev items of each of the six intents is at least v1's), the number of scripted multi-turn cases passed is at least v1's, AND the targeted error type has strictly fewer items than under v1. Otherwise v1 stays, and v2 is documented as a negative result. Dev scores after any iteration are optimistic (the author has seen the dev items).

**A18. Conservative decisions taken while building Part A (all within AGENT-DESIGN.md and these decisions; each is reversible by a later decision).**
1. Hits given to the answer: 5 products, 3 policy clauses (`PRODUCT_K`, `POLICY_K`). More would only lengthen the prompt; fewer could miss a gold SKU, which the evaluation reports as it is.
2. `lookup_order` reveals an order only for the shop's channel `vn`, only for an order number of 1 to 7 ASCII digits and an email of a plausible shape (anything else is not sent to Saleor), and compares emails in constant time. A Saleor failure raises; it is never turned into a refusal and never counts as a failed verification. The order given to the answer has no total, so no amount of money can be stated about an order.
3. A ticket id is derived from its idempotency key (`TCK-` + 10 hex digits); the file is appended under a process lock and a file lock; a ticket that cannot be written raises `TicketWriteError`, traced as `ticket_write_failed`. Only the `write_ticket` node calls `create_ticket` (a test checks every file of `app/`).
4. Guardrails err towards rejecting. A stock claim in a sentence that names two SKUs of different stock is rejected as ambiguous; a sentence that mentions the number the customer wrote next to a SKU is rejected even when it is a denial ("không phải 99k"), and the customer then reads the deterministic answer; the generic words "đang chuẩn bị" and "chờ giao" do not name an order status. An order answer that uses the words of ANOTHER status is rejected even to describe the rest of a partly shipped order ("phần còn lại chưa giao"): it falls back to the fixed statement. **Not checked, a known gap:** sizes, colours, materials and counts of days written in an answer (the four checked facts are the ones of A11, plus citations and personal data).
5. A policy answer ends with a citation line written by the code (`Nguồn: <file>, Điều <n>`) from clauses that were checked against the tool results; the deterministic policy answer is the text of the first clause, verbatim, with the same line (for the Gemini answerer this was superseded by A21: it quotes the clauses the rejected text cited, or says it has no information).
6. `handle_question` keeps the router, extractor and retriever arguments, drops `k` and `mode` (the tools decide them), and returns the agent's reply and the hits as plain dicts. Without an `answerer` it uses `TemplateAnswerer` (no LLM call). `scripts/demo_requests.py` gives it the Gemini answerer; the demo now needs up to 5 more live requests (about 18 in all, cap 40).
7. The multi-turn cases check what the real router and extractor make of hand-written messages; a case can fail because of the router or the extractor, and that is a measurement, not a defect of the case. Their expectations are data (`eval/phase6/multiturn_cases.json`), fixed before the first run; the dev messages, the probes and the demo questions are not reused (a test checks it).
8. Every dev item is the first turn of a conversation of its own, with `{order_number}` replaced as in Phase 5. A proposed ticket is answered "có" and "không" in two more conversations, in a temporary ticket file; the real `data/tickets` is never touched. A ticket request that names no order (golden source `no_answer`) is correct when the agent asks for a contact email and looks up and writes nothing.
9. The evaluation stops at a clean point when fewer than 4 live requests remain of the day's 450, or when a quota or cap error occurs: it writes `<prompt>.progress.json` and exits 2; the same command resumes after the reset, and everything finished replays from the cache.
10. Cost per 1,000 conversations is the cost of the LLM calls of the dev first turns divided by the number of dev items, times 1,000: a conversation is one dev item, the dev mix is not a traffic forecast. Latency per turn is the recorded LLM latency of the cache plus the retrieval, lookup and reply time measured in the run; it is reported as a measurement, outside the hashed result.
11. The answer prompt is written in English with Vietnamese examples (like the router and extractor prompts) and asks for a Vietnamese reply with diacritics; the fixed replies are Vietnamese with diacritics whatever the customer typed.

**A19. What the Phase 6 result reports (pre-registered).** Per intent: items, correct, accuracy; product items split into gold-SKU and `no_answer`; the scripted cases passed, with the problems of every failed turn; every bound with its limit and the largest value seen (steps per turn, clarifying questions, product searches per turn, failed verifications, confirmation asks, tickets written without a yes); the guardrail fallbacks with their rule codes and items; LLM calls per turn and tokens by component; latency p50 and p95 per turn; the theoretical paid-tier cost per 1,000 conversations with the price page named; the error analysis of every incorrect item with its category; the disclosure of A0. The scoring is `eval/phase6_scoring.py`, whose hash is in the result file.

**A20. Outcome of the pre-registered rules on the `answer_v1` run (2026-10-10, written after the run; the rules above were not changed).**
*Result.* 69 of 71 dev items correct, 13 of 13 cases, every bound held, 7 of 45 model answers replaced by a guardrail fallback (`docs/RESULTS-phase6.md`).
*A17.* E1 `stock_mismatch` affects 4 dev items (gs-002, gs-009, gs-015, gs-112), so one `answer_v2` is allowed, for that error type only; `price_mismatch`, `no_clause_cited` and `unknown_clause` affect 1 item each and E2, E3 none, so they are not targeted. v2 changes one rule and adds one example (`docs/PROMPT-LOG-phase6.md`); the guardrails stay as they are.
*What the run showed about the guardrails (reported, not tuned).* All 7 fallbacks were produced by the conservative reading of the rules, none by a fabricated fact: 5 by the ambiguous stock sentence (A18.4), 1 by a "Điều 3" quoted from inside a clause, 1 by the customer's budget in the same sentence as SKUs (the owner's rule as written, A11). One more (gs-025) was an honest "no information" that the fallback replaced by the first retrieved clause. The primary quality metric is therefore reported with the accuracy: the fallback rate per intent (`docs/RESULTS-phase6.md`, section 1). Nothing in the code of the guardrails, the fallback answers, the scoring or the parsers was changed after seeing these results (no tuning beyond the prompt-version limit); the candidate fixes are listed in the results as work to do before the final evaluation.
*A known parser gap, recorded.* The order-number parser does not read "mã 88" (gs-124), so a labelled "refuse" became an "ask for the order number": safe, but not the label. Not fixed here for the same reason.
*The claim check.* Answers that state a size, colour, material or number of days that the tool results do not support (the known gap of A18.4) were looked for with a text heuristic (`eval/analyze_phase6.py`) and by reading all 38 model-written answers: none was found. This is reported, not a guarantee.

**A21. Outcome of the A17 rule on the `answer_v2` run, and the bug-fix change that followed (2026-10-10, written after the run; the rules of A17 were not changed).**
*The A17 rule, applied as written.* v2 run: git commit `3af7dc6`, clean tree, 45 live requests (the 45 answers; every router and extractor answer came from the cache). (1) No intent has fewer correct items: product_search 24/24 and 24/24, policy_question 13/14 and 13/14, order_status 11/12 and 11/12, create_ticket, out_of_scope and smalltalk 7/7 and 7/7. (2) Cases passed 13 and 13. (3) The targeted error type, E1 `stock_mismatch`, affects 0 dev items (and 0 cases) instead of 4 (and mt-01). **All three conditions hold: `answer_v2` is adopted.** The limit of 2 versions is reached, so there is no v3. Side effects, reported: the model-written answers that were replaced by a fallback went from 7 of 45 to 2 of 45 (the five stock false alarms and the budget sentence of gs-009 are gone, because each product is now in a sentence of its own); the answer prompt is longer (input tokens of the answer calls 58,773 to 70,980, +20.8%), so the theoretical paid-tier cost per 1,000 conversations goes from 0.918 to 0.978 USD (+6.5%).
*The bug-fix change that followed.* The owner asked, after the v2 decision, for a separate bug-fix change that is not prompt tuning. It does not touch `prompts/`, the scoring, the retrieval or the cached answers, and it was made test first (a test that reproduces gs-025 fails on the code before the change).
1. *A fallback never asserts more than the text it replaces.* `bounded_fallback` (`app/agent/guardrails.py`): a rejected product answer is replaced by the products that text named (a SKU in the text or in `cited_skus`); a rejected policy answer by the clauses that text cited (at most 2, quoted whole, with the citation line); when the text named or cited nothing the evidence can back, by a fixed reply that says nothing about any product or clause (`NO_INFORMATION`, `NO_POLICY_INFO`). The order answer keeps the whole fixed statement of the verified order (it answers "where is my order" from the order's own facts and cannot say more than the order says). `TemplateAnswerer`, the answerer of the no-LLM mode, still prints the evidence as it was: it has no text to stay within. When the model gave no usable text at all (invalid JSON, blocked), the fallback is the fixed no-information reply too: no dev item was in that case.
2. *An explicit "no information" policy answer needs no citation.* `is_decline` reads a short list of phrases (folded: "không/chưa có thông tin|dữ liệu", "không/chưa tìm thấy|đủ thông tin|dữ liệu", "không/chưa đề cập") in an answer that cites no clause and writes no "Điều N"; the citation rule skips it, every other rule still applies to it. It is **not** a fallback: it is sent as the fixed `NO_POLICY_INFO` reply (the model's own words are not sent, so nothing said next to the decline can reach the customer) and counted apart (`AnswerStats.declines`, `Answer.declined`, the `declines` column of the analysis). "không có quy định ..." is not a decline: it is a claim about the rules and needs a citation. When the relaxed search found suggestions but a fallback names none, the notice "Nếu bỏ điều kiện ..." is not written (nothing follows it).
3. *The order-number parser reads "mã 88".* "mã 88", "mã số 88", "mã đặt hàng 88", "mã order 88", with or without diacritics. Not read (tests): "88k", "88 nghìn", "88.000đ", "mã giảm giá 88", "mã sản phẩm 88", "mã size 38", "size 38", "mã vận đơn 88", "mà 88". The tests found two older defects of the same parser, fixed in the same change: "mã vận đơn 88" (a tracking number) and an amount such as "đơn 459.000đ" were read as an order number. Known limit, recorded: "áo mã 38" (a product code or a size) reads as order 38; the number is only a candidate for a lookup, which still needs the owner's email, and a wrong candidate counts as one failed verification at most.
The runner and the analysis report declines apart from fallbacks (`declined` per item, `declines` in the guardrails block); the committed results of v1 and v2 predate it and are not rewritten.
*What this change does not do.* gs-027 (a "Điều 3" cross-reference written inside the quoted clause 6) and the budget-in-a-sentence-with-SKUs reading of the owner's price rule are still rejected by the guardrails as before; they are false alarms that cost a fallback, listed as work for the owner, not changed here because the instruction did not name them and the guardrail is the part to change last. The retrieval miss of gs-025 is still a retrieval miss.
*How the numbers were made.* The official runner refuses a dirty tree, so the after-numbers come from the offline replay of the cache (`eval/analyze_phase6.py`, 0 live calls) and are labelled so; its `before_after_the_code_change` block compares them with the committed official result item by item. Only two items differ: gs-025 (a fallback that quoted an irrelevant clause became the honest no-information reply, still incorrect: the gold clause was not retrieved) and gs-124 (the known parser gap: now `refuse`, correct). **The dev gain (order_status 11/12 to 12/12) is the known parser gap fixed with the dev item in hand, not an independent estimate**: only the test split can say whether the fixes generalise.
*Conservative choices taken without asking, so that the owner can reverse them:* the decline list is narrow (a missed decline costs a fallback to the fixed reply, never an invented one); the decline reply is the fixed text, not the model's; a fallback with nothing named says nothing (also for the unusable-output case, where the old fallback printed the first clause or the first three products); the order fallback is unchanged.
