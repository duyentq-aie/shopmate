# Phase 4 decisions: experiment 1, diacritic-insensitive lexical retrieval (2026-10-10)

One change, measured: a new lexical signal that ignores diacritics, compared with the Phase 3B baseline `hybrid`. This file is written **before any Phase 4 number exists**. Nothing was evaluated while building it: the only runs were rehearsals of the index build on a scratch Qdrant collection (deleted afterwards) with hand-written smoke queries; no golden item, dev item or metric was involved. The test split was not read. Hypothesis, from the Phase 3B error analysis: all 3 complete misses were khong_dau queries, so a lexical branch that folds diacritics should help them. Known risk: folding also merges words that differ only by diacritics ("phí" and "phi công" both contain the token `phi`), which may hurt co_dau queries.

**R17. The folded lexical vector: BM25-style weights on diacritic-folded syllables, IDF by Qdrant (owner's choice, option A).**
- `fold(text)` (`app/retrieval/folding.py`): lowercase, Unicode NFD, strip combining marks, `đ` → `d`. The same function is applied to documents, queries and the perturbation set. Tokens are `[a-z0-9]+` runs of the folded text: syllables, numbers, "400k". No teencode expansion, typo repair or word segmentation (those are other experiments).
- Document side (`app/retrieval/lexical.py`): `tf·(k1+1) / (tf + k1·(1 − b + b·dl/avg_len))` per token; query side: 1.0 per distinct token; the vector is created with Qdrant's `modifier = idf`, so the score is BM25. **`k1 = 1.2`, `b = 0.75` are the textbook defaults and were not tuned on dev.** `avg_len = 70.9` is pinned (so a document's vector never depends on other documents): the mean number of folded tokens of the 269 indexed documents is 70.91 (products 70.7, policies 73.8).
- Token id = first 4 bytes of blake2b as an unsigned 32-bit int. The corpus has 489 distinct folded tokens and no collision; every build checks that (`check_no_collisions`) and aborts before writing anything otherwise.
- Folding merges 113 of the 489 folded tokens across more than one accented form (e.g. `do` ← đô/đỏ/đồ/độ/đỡ/do, document frequency 160; `phi` ← phi/phí, df 9). That ambiguity is the cost the experiment measures.
- Rejected: bge-m3 sparse on folded text (a model pass per query, weights learned on accented text); IDF baked into the document weights (vectors would depend on the whole corpus); Qdrant full-text payload indexes (boolean filters, no score to fuse); BM25 and RRF outside Qdrant (would confound the fusion implementation with the signal).

**R18. A new collection `shopmate_vn_v2`; `shopmate_vn` is frozen.**
- Verified on Qdrant 1.19.1: neither a sparse nor a dense named vector can be added to an existing collection (`Not existing vector name`). The folded vector therefore lives in a new collection with three named vectors (`dense`, `sparse`, `folded`).
- `dense` and `sparse` are **copied** from `shopmate_vn`, not recomputed: no model run, no floating-point drift from re-embedding. Verified on all 269 real vectors: bit-identical dense, identical sparse and payload, and identical R16-ordered results. A digest of the copied vectors is compared between source and target (`SeedMismatch` otherwise) and recorded in the manifest.
- `scripts/build_index.py` builds v2 only and refuses to target `shopmate_vn` (the Phase 3A/3B index), so every Phase 3B configuration stays runnable and reproducible. Re-indexing is idempotent; changing the lexical config rewrites only the folded vector and one payload field.

**R19. The manifest names the collection and protects every run.**
- `data/index/manifest.json` carries `collection`, and `Retriever`, the eval runner and the integration tests use it (`app/retrieval/manifest.active_collection`). A v2 manifest also records `lexical` (config + fingerprint), `vectors_digest` (dense + sparse) and `derived_from` (source collection and its digest).
- `index_problems` (eval runner) now also checks: the lexical fingerprint of every point, the query-side lexical config, that the folded vector exists with the IDF modifier, that a collection with a folded vector is matched by a manifest that declares one, and that the live dense/sparse digest equals the manifest's. These checks run for **every** configuration, baseline included, so a drifted baseline vector cannot go unnoticed.
- The deterministic section of the Phase 3B modes keeps exactly its Phase 3B shape (guarded by a test against the committed `hybrid-none.json`); fields are only added for the new modes (`lexical_fingerprint`) and for the perturbed queryset (`config.queryset`, `perturbation_sha256`).

**R20. What "the baseline hash reproduces" means.**
`deterministic_sha256` includes `provenance.git_commit` and `index_manifest_sha256`, so it can only be reproduced byte for byte at the commit and with the manifest of the original run. Done before any change: at `d8b4a61` (clone outside the repo, live index) `hybrid-none` reproduced `0198d72d71ac96d8f3ebe7559ae790b6c5c3c25ecde69cfcb28165634bf8249a` exactly, with the same dev split and manifest. After this change the baseline is re-run in `eval/results/phase4-exp1/`; the check (`eval/compare_exp1.reproduction_check`) requires `items` and `aggregate` to be identical and the provenance to differ **only** in `git_commit` and `index_manifest_sha256`. Because the manifest is tracked and the runner refuses a dirty tree, re-indexing is followed by a commit of the manifest before any evaluation run.

**R21. The decision rule (amended 2026-10-10, before any number exists).**
The first version used the 6 real khong_dau items (n = 6) as the primary test; it would almost certainly fail whatever the true effect, so it was replaced. Final rule, in code (`eval/exp1_rule.py`, unit-tested, committed before any run) and not to be changed after results exist. For each candidate (`dense_sparse_folded`, `dense_folded`) against the baseline `hybrid`, filters = none, adopt only if **both**:
1. on the **perturbation set**, MRR improves vs the baseline and the paired-bootstrap 95% CI of the per-item difference excludes 0 (`ci_low > 0`, 10,000 resamples, seed 20261009, as in Phase 3B), pooled over its 33 items; **and**
2. on the **original dev set**, overall MRR (all query styles, answerable items) is not worse (point estimate ≥ baseline, up to float noise of 1e-12) for **both** product_search and policy_question.
If both candidates pass: the larger perturbation gain wins, unless the two gains' CIs overlap heavily, in which case the simpler/faster configuration (`dense_folded`: two branches, no bge-m3 sparse) wins. If neither passes the baseline stays and the experiment is recorded as a documented negative result. Operationalisations chosen here, before results: "overlap heavily" = (length of the intersection of the two CIs) / (length of the shorter CI) ≥ 0.5; "simpler/faster" = `dense_folded`. The two-candidates multiple-comparison caveat is stated in the results. **Secondary, reported but not deciding, labelled exploratory:** the 6 real khong_dau items (pooled over intents) and the items whose question has no diacritic at all (machine-detected, includes khong_dau-like teencode queries).

**R22. The perturbation set (`eval/perturbation/dev_folded.json`).**
Every answerable dev retrieval item (19 product_search with SKUs, 14 policy_question) with its question passed through `fold`, same gold: 33 items, of which 24 changed and 9 had no diacritics to begin with (their baseline-vs-candidate difference comes from the added branch alone). Built deterministically from the dev split only (`eval.perturbation.dev_folded`, `--check` verifies the committed file), saved with a content hash and the hash of its source items; the runner refuses a file that was edited or no longer matches the dev items. **Limitation, written into the file:** machine-stripped text is not how real users type (no typos, no abbreviations beyond the original questions), so it is a robustness test of diacritic handling, not a substitute for real queries.

**R23. Risks recorded before the results.**
- **Ties inside the folded branch.** Documents of equal length with the same matching tokens get exactly equal BM25 scores. Measured on the real index with 54 hand-written queries: 53 had exact ties in the folded branch's top 50, the largest group 11 documents. Qdrant ranks such ties in a fixed internal order (the order points were inserted: documents sorted by key), arbitrary but not random: 162 query × filter cases × 20 repeated calls gave 0 unstable result lists in `hybrid`, `dense_sparse_folded` and `dense_folded`. R16's client-side sort cannot repair ties inside a branch (it only orders fused ties), so the folded branch carries an arbitrary-but-fixed tie order. The 20× determinism integration test covers the new modes on the dev queries once the index is built. If a rebuild with a different document order were ever used, tie order, and possibly results, could change.
- **RRF weight.** `dense_sparse_folded` has two lexical branches out of three, so dense carries 1/3 of the RRF weight instead of 1/2; its effect mixes "a new signal" with "less dense weight".
- **Small n.** 19 + 14 answerable dev items; the perturbation set is the only place where a paired bootstrap has a realistic chance to exclude 0.

**R24. Scope and outputs.**
Results go to `eval/results/phase4-exp1/` (runner option `--results-dir`, restricted to below `eval/results/`), so the committed Phase 3B result files are never touched. Runs: baseline, `dense_sparse_folded`, `dense_folded` × filters none and routing, on the dev set and on the perturbation set; oracle for policy_question only (the product oracle is a tautology, Phase 3B). `eval/compare_exp1.py` produces the comparison: reproduction check, paired tables per intent and query style, the rule's verdict, exploratory subsets, oracle, and every co_dau item whose first-gold rank got worse with the documents that newly outrank gold and which query words matched them only through folding. Out of scope: rerankers, LLM query rewriting, diacritic restoration, routing, filter extraction, Jev.
